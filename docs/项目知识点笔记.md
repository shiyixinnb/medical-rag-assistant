# 医疗 RAG 问答系统 · 知识点笔记

> 用途：学习笔记 + 面试复习 + 复盘材料。
> 组织方式：**按知识领域**（不是按文件、也不是按调用流程）。每个知识点都标了「本项目怎么做的」，因为知识要落到具体决策上才算真的懂。
> 项目实测规模：`llm` 接入层 **11 个子包 / 41 个类**，全项目 56 个 `.java`。

## 第 0 章 · 概念地基（传统 Java 视角）

### 0.1 先建立映射：你已有的知识 → AI 概念

| 你已经会的 | 对应的 AI 概念 | 关键差异 |
|---|---|---|
| `hashCode()` + `HashMap` | **Embedding（向量）** | hashCode 只保证"相等则相同"；Embedding 保证**语义相近则距离相近** |
| SQL `ORDER BY 距离 LIMIT N` | **向量检索** | 距离是"语义距离"，没有可用索引时就是全表算距离（暴力检索） |
| MyBatis 拼 SQL | **Prompt 模板** | Prompt 是"用自然语言写业务逻辑"，且**不受编译器检查** |
| Sentinel / Hystrix 熔断 | **模型熔断** | 思路完全一样，但**流式场景要用 `asyncEntry`**（见 §6.4） |
| 主库挂了读从库 | **模型主备降级** | 一样，但要注意"流式输出已发出不可撤回"（见 §6.5） |
| 脏数据 / 不抛异常的错误 | **幻觉（Hallucination）** | 模型**永远返回 200**，错的内容也长得像对的，这才是它危险的地方 |
| 按 `type` 分派 Handler | **意图路由** | 分类器可能是"关键字加权打分"，不一定需要模型 |
| `@Transactional` 保证一致性 | **无对应物** | 一次问答有多次外部调用（向量库+模型），**没有事务**，只能靠补偿和降级 |

> 这张表值得反复看：**AI 应用开发 80% 的工程问题是传统后端问题的变体**，剩下 20% 才是新的。

### 0.2 Token（词元）
- 模型不是按"字"处理文本，而是按 **token**。中文大致 1 个字 ≈ 1~2 个 token，英文 1 个单词 ≈ 1~3 个 token。
- **为什么必须懂**：Token 决定三件事 —— 费用、上下文上限、以及**输入比输出便宜得多**（所以 RAG 里塞资料比让模型自己生成划算）。

### 0.3 Embedding（嵌入）
- 把文本映射成一个**定长浮点数组**。本项目用 BAAI/bge-m3，**1024 维**。
- 关键性质：`embedding("中暑怎么急救")` 与 `embedding("热射病处理方法")` 的向量距离**很近**，尽管没有一个字相同。
- **维度必须固定**：索引建成 1024 维后，换一个 768 维的模型**必须重建索引**，否则写入报错。这是换 embedding 模型时最容易忘的一步。

### 0.4 相似度与阈值
- 常用 **余弦相似度**，范围 [-1, 1]，越接近 1 越相似（本项目配置 `similarity-threshold: 0.5`）。
- **阈值的意义是"宁缺勿滥"**：低于阈值就不该把这条资料喂给模型。因为**垃圾资料比没有资料更糟** —— 模型会一本正经地基于错误资料编答案。

### 0.5 幻觉（Hallucination）
- 定义：模型生成了**流畅、自信、但事实错误**的内容。
- **工程上的应对不是"让它别编"，而是三道防线**：
  1. 检索阶段给足正确资料（资料对，答案大概率对）
  2. Prompt 里强制"只能依据资料回答，资料没写就说没写"
  3. **服务端校验输出** —— 让模型标注引用编号，返回前检查编号是否越界（本项目 `AnswerMetaParser` 做这件事），越界即告警

### 0.6 温度（temperature）
- 控制输出随机性。0 ≈ 确定性输出，1+ ≈ 更发散。
- **医疗/知识库场景应取低值**（0~0.3）：要的是"照资料复述"，不是"发挥创意"。

### 0.7 Tool / Function Calling
- 让模型"调用你的 Java 方法"：你提供工具的描述和参数 schema，模型决定何时调用、传什么参数。
- **本质是让模型输出一段结构化 JSON**，再由框架反射调用。
- 适用场景：需要**实时或私有数据**（查天气、查数据库）。本项目未用（RAG 已覆盖知识类需求），但项目里有 `WeatherTool` 示例。

### 0.8 RAG vs 微调（面试必问）
| | RAG（检索增强） | 微调（Fine-tuning） |
|---|---|---|
| 知识存在哪 | 外部知识库 | 模型参数里 |
| 更新成本 | 改数据即可，**分钟级** | 重新训练，**天级 + 成本高** |
| 可溯源 | ✅ 能给出引用原文 | ❌ 说不清依据 |
| 数据合规 | 数据不进模型，**可控** | 数据要拿去训练，**风险高** |
| 适合 | 知识频繁更新、要溯源、数据敏感 | 要改**风格/格式/语气** |

**结论：医疗场景（知识更新快 + 必须溯源 + 数据不能出内网）几乎必然选 RAG。**

## 第 1 章 · RAG 全链路

### 1.1 为什么需要 RAG
模型的知识有两个硬限制：**训练数据有截止时间**、**看不到你的私有数据**。RAG 的思路是"**不教模型，而是每次提问时把相关资料递给它**"。

### 1.2 两个阶段（务必分开理解）

**索引期（离线，知识变更时跑一次）**
```
原始文档 → 切分(chunk) → 向量化(embedding) → 写入向量库 + 元数据
```

**查询期（在线，每次提问）**
```
问题 → 意图判定 → 权限判定 → 问题向量化 → 向量检索 → 拼装 Prompt → 调模型 → 结构化出参
```

> **痛点**：这两阶段必须**保持同步**。本项目踩过这个坑 —— 知识库改了但没重建索引，检索结果就是旧的。所以在增删改接口里内置了自动 rebuild，批量 SQL 导入后要手动 `POST /api/knowledge/rebuild`。

### 1.3 切分（Chunking）的取舍
- **切太小**：一句话被切开，语义不完整 → 检索到了也答不准
- **切太大**：一条资料占满上下文，噪声多、成本高
- 常见做法：按语义段落切（本项目按知识条目切），并保留**重叠区**避免边界信息丢失
- 配套参数：本项目 `max-snippet-chars: 700` —— 单条片段注入 Prompt 的最大长度，超长截断，防止一条资料挤掉其他资料

### 1.4 关键参数
| 参数 | 本项目值 | 含义与调优方向 |
|---|---|---|
| `top-k` | 4 | 召回条数。调大召回更全但噪声多、成本高 |
| `similarity-threshold` | 0.5 | 相似度下限。调高更精准但可能召回为空 |
| `max-snippet-chars` | 700 | 单片段注入上限 |

### 1.5 引用溯源
让模型在回答里标注 `[1] [2]` 对应第几条资料，然后**服务端校验编号合法性**。
- 好处一：医生能核对原文（医疗场景的硬要求）
- 好处二：**编号越界是幻觉的明确信号**，可以主动告警而不是默默返回

### 1.6 RAG 的两种失败模式（排查时先分清）
| 失败模式 | 现象 | 排查方向 |
|---|---|---|
| **召回失败** | 检索压根没查到对的资料 | 看召回清单：切分是否合理、embedding 是否匹配、过滤条件是否过严 |
| **生成失败** | 资料明明在，模型答错/答偏 | 看 Prompt：资料是否被正确注入、是否被其他指令干扰、温度是否过高 |

> 本项目把召回清单连同相似度分数一起返回给前端（`citations`），**就是为了让这两类问题一眼可分**。

## 第 2 章 · 向量库与索引（Redis Stack / RediSearch）

### 2.1 为什么选它
1. 本机已有 Redis，Redis Stack 自带 RediSearch，**零额外部署**
2. 数据量万级以内性能足够，独立部署 Milvus 属于过度设计
3. **核心诉求是元数据过滤**（按数据域隔离），RediSearch 的 TAG 过滤直接支持

### 2.2 RediSearch 的三种字段类型（必须分清）
| 类型 | 用途 | 本项目实例 |
|---|---|---|
| `TAG` | **精确匹配**、可过滤 | `domain`、`tenantId`、`patientId`、`category` |
| `TEXT` | **全文检索**、分词 | `title`、`source` |
| `VECTOR` | 向量相似度 | `embedding`（1024 维） |

> **选型原则**：要 `==` 过滤用 TAG；要模糊/分词搜用 TEXT。
> ⚠️ 本项目踩过的坑：`title` 一开始想用 TAG，但**标题含空格和中文**会撞 TAG 的分隔符语义，改用 TEXT 才正常。

### 2.3 索引 schema 只返回"声明过的"字段
**现象**：JSON 原文里明明有 `title`，检索出来 `title=None`。
**根因**：RediSearch 索引只索引你**显式声明**的字段，没声明的字段取不出来。
**修法**：把字段补进 `MetadataField` 列表，然后**必须 drop 索引重建**（`FT.DROPINDEX <idx> DD` 后重启），否则旧 schema 一直生效。

### 2.4 🚨 TAG 值不转义 = 静默失效（本项目最核心的坑）
- **现象**：`tenantId == 'HOSP-A'` 报 `Syntax error at offset N near A`，或**静默命中 0 条**。
- **根因**：RediSearch 把 `-` 当**标点分隔符**，`{HOSP-A}` 被解析成两个词。而 Spring AI 的过滤器转换器**不转义 TAG 值**。
- **两种失效形态要分清**（这点最坑）：
  - `HOSP-A` → **报语法错**，日志里能查到
  - `P-1001` → **静默命中 0 条，不报任何错**，你只会以为"知识库里本来就没这条"
- **修法**：值先转义再塞进 `Filter.Value`。转义规则：ASCII 非 `[A-Za-z0-9_]` 的字符加 `\`。
- ⚠️ **中文不能转义**：实测 `@category:{\病历摘要}` 命中 0 条，而 `{病历摘要}` 命中 2 条 —— 转义规则要区分 ASCII 和中文。
- **判据**：日志里「索引过滤不可用」「跨租户片段已被丢弃」的计数**必须恒为 0**，把它当回归指标。

### 2.5 key 前缀隔离
本项目：公共域 `embedding:public:`、患者域 `embedding:patient:`，配合两个独立索引。
**好处**：物理上分开，即使过滤逻辑写错，也不会跨域读到数据。

### 2.6 向量索引算法
`FLAT`（暴力精确）vs `HNSW`（近似，快但可能漏）。数据量大时用 HNSW，代价是**召回不是 100% 精确** —— 这是一个典型的"性能换准确率"取舍。

## 第 3 章 · Spring AI 框架（本项目用 1.0.0-M7）

### 3.1 `ChatModel` vs `ChatClient`
- **`ChatModel`**：底层接口，`call(Prompt)` 返回 `ChatResponse`。**你要自己拼消息列表**。
- **`ChatClient`**：上层门面（链式 API），管 Prompt 模板、Advisor、会话记忆。**日常用这个**。
- 本项目的用法：`ChatClient.builder(model).build()` → `spec.user(...).call()/stream()`。

### 3.2 Advisor 机制
类似**拦截器/过滤器链**（Web 里的 `Filter`、AOP 里的 `Around`）。它能在"请求前"和"响应后"插入逻辑。
- `QuestionAnswerAdvisor`：把"检索 + 拼进 Prompt"封装成一个 Advisor
- **本项目为什么不用它**：它做不了**按数据域隔离检索**。我的场景需要先判权限、再决定查哪个索引、还要按 `tenantId`/`patientId` 收敛。所以自己实现 `DomainAwareRetriever`。
- **通用原则**：框架封装适合快速验证；**一旦触及权限边界，就要自己拿回控制权**。

### 3.3 里程碑版（M7）与正式版的差异 ⚠️
- M7 是**里程碑预览版**，API 与 GA 差异大，**照抄网上 GA 教程会直接编译不过**。
- 踩过的具体差异：advisor 的**包路径**变过、`RetryTemplate` 的**默认值**变过。
- **升级路径**：`pom` 里 `spring-ai.version` 改一处（`spring-ai-bom` 统一管版本）。升级后必须重点回归：RediSearch 转换器行为、advisor 包路径、自动配置的 `metadataFields`。
- **怎么确认 API 签名**（比搜文档可靠）：`javap -c -p -cp <jar> <class>` 反编译看常量池，或写个探针类直接 `new XXX(...)` 试。

### 3.4 🚨 `RetryTemplate` 默认值陷阱（很隐蔽）
- M7 默认的 `RetryUtils.DEFAULT_RETRY_TEMPLATE` 是 **10 次指数退避**，最高 180 秒。
- **后果**：模型内部自己重试好几分钟，导致你在外层写的"超时切下一个模型"**永远轮不到执行** —— 看起来降级链配了却没用。
- **修法**：给每个模型注入 `RetryTemplate.builder().maxAttempts(1).build()`，把重试权收回到自己的门面层。

## 第 4 章 · 模型治理（可靠性工程）

### 4.1 模型注册表（配置驱动）
本项目 `app.llm.models.*` 声明 4 个模型，`ModelRegistry` 启动时构建：

| 模型 | 能力 | 优先级 | 超时 | 定位 |
|---|---|---|---|---|
| `qwen-med` | REASONING | 5 | 60s | 院内私有化（**未配 Key 时自动跳过**） |
| `deepseek-chat` | GENERAL | 10 | 30s | 常规问答主通道 |
| `deepseek-reasoner` | REASONING | 20 | 60s | 复杂推理/急诊分诊 |
| `glm` | GENERAL | 30 | 30s | 主备降级的备选 |

**设计要点：缺 API Key 的模型"跳过并告警"，而不是让应用启动失败** —— 这样私有化模型可以先占位、开通后填 Key 自动生效，不用改代码。

### 4.2 能力路由
按**意图**选模型，而不是所有问题都用最强模型（贵且慢）：
- 本项目 7 个意图：`EMERGENCY_TRIAGE`（急诊分诊）、`DRUG_QUERY`、`GUIDELINE_QUERY`、`PATIENT_RECORD_QUERY`、`COMPLEX_REASONING`、`GENERAL_QA`、`CHITCHAT`
- 意图带两个标记位：`preferReasoning`（是否偏好推理模型）、`requiresPatientDomain`（是否必须患者域授权）
- 路由参数：`reasoning-model` / `general-model` / `reasoning-length-threshold: 80`（超 80 字视为推理密集）
- **`IntentClassifier` 用关键字加权打分 + 长度加成 + 追问继承 + 兜底**实现，不需要调模型 —— **能不用模型判断的事就别用**，省一次调用就是省延迟和省钱

### 4.3 主备降级链
```yaml
fallback:
  deepseek-reasoner: [deepseek-chat, glm]
  deepseek-chat: [glm]
  glm: [deepseek-chat]
```
未配置的会自动追加 `default-model` 兜底。**降级链是有向图，允许互备**。

### 4.4 熔断三态
| 状态 | 含义 |
|---|---|
| `CLOSED` | 正常放行 |
| `OPEN` | 已熔断，直接拒绝（**不再调模型**，省时间也省钱） |
| `HALF_OPEN` | 静默期结束，放少量请求探测，成功则恢复 |

本项目参数：失败率阈值 `0.5`、最小样本 `5`、统计窗口 `10s`、静默 `20s`、慢调用阈值 `15s`（**慢也算失败**）。

### 4.5 熔断双后端
`backend: auto` —— 类路径有 Sentinel 就用 Sentinel，否则用自研滑动窗口。
**设计价值**：把熔断抽象成 `ModelCallGuard` 接口，**换实现不改业务代码**。这是"可替换依赖"的典型做法。

### 4.6 重试与降级的关系（重要的洞察）
**重试次数越多，降级越慢。** 如果单模型重试 10 次 × 30s 超时 = 300s，用户早就走了。
所以本项目把重试压到 `max-attempts: 2` + `backoff-ms: 300`，**宁可快速切下一个模型，也不在一个模型上死磕**。
> 一般原则：**外层（业务）的重试要少，内层（网络瞬断）的重试可以稍多**。

### 4.7 超时分层
- **连接超时**（5s）：连不上就该快速失败
- **读超时**（30s / 推理模型 60s）：**推理模型天生慢，超时要给宽** —— 这是配置里唯一按模型差异化设置的值

## 第 5 章 · 数据安全与合规（本项目的差异化价值）

### 5.1 fail-closed（默认拒绝）
**含义**：任何一步判断不出"这个人有权看这份数据"，就**拒绝作答**；而不是"没查到限制条件就当没限制"。
**理由**：医疗场景里，**"答不出来"的代价远低于"答错"**。把 A 机构的患者数据答给 B 机构，是事故不是 bug。
**本项目做法**：未授权时**既不检索也不调用模型**，直接返回拒答，`modelId=none`。

### 5.2 三层纵深防御
| 层 | 做法 | 拦截什么 |
|---|---|---|
| ① 物理隔离 | 公共域/患者域**独立索引 + 独立 key 前缀** | 跨域读到的可能 |
| ② 索引过滤 | `domain == 'PATIENT'` + `tenantId == 'x'`（+ 点名患者时 `patientId == 'x'`） | 跨机构召回 |
| ③ Java 侧复核 | 返回的 Document **再核一遍** domain/tenantId/patientId，不匹配丢弃并计 ERROR | 第②层静默失效时的兜底 |

**为什么必须有三层**：因为第②层真的会**静默失效**（见 §2.4）。**安全边界不能只依赖单层** —— 这是从那次踩坑得到的最大教训。

### 5.3 ⚠️ tenantId 自证授权问题
**反模式**：`tenantId` 由**客户端传参**、服务端直接采信 → 等于租户隔离**靠调用方自觉**，任何人改个参数就能越权。
**正确做法**：`tenantId` 必须由服务端**从鉴权上下文（登录态/Token）推导**，绝不能信任请求体里的值。
> 本项目因为是对外演示，`tenantId` 仍走请求参数，但代码注释里明确标了这个限制。**面试时如果被问到，主动说出这一点是加分的。**

### 5.4 确定性拒答 vs 让模型判断
**错误做法**："把资料给模型，让它自己发现资料里没有这个患者。"
**本项目做法**：用**正则从问题里抽出患者标识**（`patient-id-pattern`），检索时收敛到该标识；该患者不属于当前 `tenantId` 就**查空 → 走既有拒答分支**。
**价值**：把"模型可能判断错"变成**代码层面的确定性行为**。
> 细节：那个正则 `(?<![A-Za-z0-9])[A-Za-z]{1,4}-[0-9]{2,}(?![0-9])` 要求"字母段后必须跟数字"，所以**不会误伤 `HOSP-A` 这类院区标识**。

### 5.5 可观测性（让"看不见的行为"可验证）
把安全相关的异常路径都做成**可计数指标**，作为回归判据：
- 「索引过滤不可用」计数 → 期望 **0**
- 「跨租户片段已被丢弃」计数 → 期望 **0**
- 「模型降级」次数 → 反映主备链健康度

**理念**：安全设计如果不可观测，就等于没有 —— 没人敢给一个"看不见行为"的系统签字。

## 第 6 章 · 流式输出（SSE）

### 6.1 为什么必须流式
**推理模型首字延迟实测 15~25 秒**。非流式下用户要对着空白等这么久；流式下第一个字很快就出现，体验完全不同。
> 关键认知：**流式优化的是"感知延迟"，不是"总耗时"**。总耗时可能一点没变。

### 6.2 SSE 协议要点
```
event: delta
data: {"text":"中暑"}

```
- 一个事件以**空行**结束
- 以 `:` 开头的是**注释行**（心跳），客户端应忽略
- 一个事件可以有**多行 `data:`**，客户端必须用 `\n` 拼接
- 客户端应剥掉字段值**开头的一个空格**（规范规定）

### 6.3 🚨 `data` 不能承载裸文本（本项目踩的坑）
**根因**：Spring 的 `SseEmitter` 对 `String` 是**原样写出、不做 JSON 序列化**（即便传了 `APPLICATION_JSON`）。于是：
1. **行首空格被吃**：规范要剥一个空格，而 Spring 不补分隔空格 → 正文里真实的行首空格被剥掉
2. **换行被拆**：正文的 `\n` 变成多个 `data:` 行

**修法**：一律包成 JSON 对象 `{"text":"..."}`，首字符恒为 `{`，空格和换行都变成转义字符，**字节级保真**。
**通用原则**：**协议字段要设计成"不可能歧义"的形式**，别依赖客户端解析规范的细节。

### 6.4 流式下的熔断必须用 `asyncEntry`
- `SphU.entry()` 是**线程本地**的，`exit()` 时必须在同一线程
- 但流式的回调（`doOnComplete`/`doOnError`）可能跑在**模型 SDK 的 IO 线程**上 → 找不到原 Entry
- 所以用 `SphU.asyncEntry(...)`，并用 `AtomicBoolean` 保证 `exit()` **恰好一次**
- **用户主动取消（`SignalType.CANCEL`）只释放半开探测位，不能记失败** —— 否则用户点几次"停止生成"就把模型误熔断了

### 6.5 降级只能在首 token 之前
用 `AtomicBoolean emitted` 标记是否已吐出内容：**一旦流里有 delta，就不再换模型**。
**理由**：流式输出"已发出不可撤回"，中途换模型前端会看到**两段风格不同的文字拼在一起**。

### 6.6 `SseEmitter` 的正确用法
```java
SseEmitter emitter = new SseEmitter(180_000L);   // 超时要远大于模型读超时
Disposable sub = flux.subscribe(emitter::send, emitter::completeWithError, emitter::complete);
emitter.onCompletion(sub::dispose);   // ← 三处都要 dispose
emitter.onTimeout(() -> { sub.dispose(); emitter.complete(); });
emitter.onError(e -> sub.dispose());
```
**`dispose()` 是必须的**：客户端一断开，若不断开上游订阅，**模型会在后台继续生成，白烧 token**。

### 6.7 前端解析（用 `fetch` + `ReadableStream`，不用 `EventSource`）
**为什么不用原生 `EventSource`**：它只能发 **GET**、不能带 JSON body，而提问是 POST + 结构化参数。
```js
const reader = resp.body.getReader()
const decoder = new TextDecoder('utf-8')
for(;;){
  const {value, done} = await reader.read()
  if(done) break
  parser.push(decoder.decode(value, {stream:true}))  // ← stream:true，中文跨 chunk 才不会被切坏
}
```
**前端解析三个必须做对的地方**：多行 `data` 用 `\n` 拼、行首只剥一个空格、`TextDecoder` 要传 `{stream:true}`。

## 第 7 章 · 多轮会话

| 配置 | 本项目值 | 含义 |
|---|---|---|
| `ttl-minutes` | 120 | 会话过期时间 |
| `history-turns` | 10 | **送入模型**的最近轮数 |
| `max-stored-messages` | 40 | Redis 中**保留**的消息上限 |
| `key-prefix` | `app:llm:` | key 前缀，避免和其他业务撞 |

**两个容易混的概念**：`history-turns` 是"给模型看多少"，`max-stored-messages` 是"存多少"。**存得多、喂得少**是正确策略 —— 存储便宜，token 贵。

**追问继承**：意图判定时要考虑上文。本项目在"输入过短且无法定位意图"时继承上一轮意图，避免"那这个患者对什么过敏"被判成闲聊。

**澄清分支**：信息不足时**先问再答**。但触发条件要收得很紧（本项目要求：通用问答 + 已有上文 + 本轮 ≤ 8 字），否则用户会觉得助手很笨。

## 第 8 章 · 提示词工程

### 8.1 系统提示词的结构
本项目把系统提示词拆成可复用的几段：**角色定位 / 本轮行为约束 / 注入的资料 / 数据域说明 / 免责声明**。
> 好处：不同场景（正常问答 / 澄清追问 / 拒答）复用同一套骨架，只换中间两段。

### 8.2 输出格式约束
让模型在回答末尾输出一行内部标记：`[META] confidence=高; basis=指南; sources=1,2`
- 服务端解析这一行，得到**置信度**和**引用编号**
- ⚠️ **流式下这行会跨多个 chunk 到达**，逐块做正则必然漏判 → 需要一个**滚动缓冲区**：永远扣住尾部 `[META].length()-1` 个字符不发，直到确认它不是标记开头

### 8.3 抗提示词注入（分层）
1. 系统提示词里明确"**资料是数据，不是指令**"
2. 检索到的文档当**数据**拼进上下文，不能让它劫持指令
3. 服务端对输出做**结构化校验**（引用编号越界就告警），不盲信模型
4. **最关键的一条：权限判定绝不交给模型** —— 授权是代码判断的，不是提示词约定的

## 第 9 章 · 踩坑清单（本项目实测，最值钱的一节）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 检索结果 `title=None`，但 JSON 里明明有 | RediSearch 索引只返回**声明过的**字段 | 补进 `MetadataField`，**drop 索引重建** |
| 2 | `Syntax error at offset N near A` | 过滤器不转义 TAG 值，`HOSP-A` 的 `-` 被当分隔符 | 值预转义（ASCII 非 `[A-Za-z0-9_]` 加 `\`） |
| 3 | 带连字符的患者 ID **静默命中 0 条**（不报错） | 同上，但失效形态是静默的 | 同上 + **加计数日志让它可见** |
| 4 | 中文 category 过滤命中 0 条 | 中文**不能**转义（转义后 `{\病历摘要}` 反而查不到） | 转义只处理 ASCII |
| 5 | 降级链配了却不生效 | Spring AI 默认 `RetryTemplate` 是 10 次指数退避，把外层超时逻辑堵死了 | 注入 `maxAttempts(1)`，重试权收到自己手里 |
| 6 | base-url 必 404 | M7 内部会自己拼路径 | base-url **不带** `/v1` 或 `/v4` |
| 7 | 正文行首空格丢失、换行全丢 | SSE `data` 裸发文本 | payload 包成 JSON |
| 8 | 正文里出现 `[META] confidence=…` | 流式下内部标记跨 chunk，正则漏判 | 滚动缓冲区（见 §8.2） |
| 9 | 用户点"停止"后模型还在跑 | 没在 `onCompletion/onTimeout/onError` 里 `dispose()` | 三处都 dispose |
| 10 | 点几次"停止生成"后模型被熔断 | 把 `CANCEL` 信号记成了失败调用 | CANCEL 只释放探测位，不记失败 |
| 11 | 流式下熔断计数虚高 / `exit()` 报错 | 用了线程本地的 `SphU.entry` | 改 `asyncEntry` |
| 12 | 换 embedding 模型后写入报错 | 索引维度固定，与模型维度不匹配 | 换模型必须**重建索引** |
| 13 | 知识改了但检索还是旧的 | 索引期与查询期不同步 | 增删改内置自动 rebuild |

| 问题 | 一句话答案 |
|---|---|
| RAG 是什么 | 不教模型，每次提问把相关资料递给它 —— 知识外置，可更新、可溯源、数据不出内网 |
| RAG vs 微调 | 知识高频更新 / 要溯源 / 数据敏感 → RAG；改风格格式 → 微调 |

| 为什么要元数据过滤 | 多租户/多数据域隔离 —— 过滤失效等于越权访问 |
| 为什么用 Redis 做向量库 | 已有 Redis、数据量万级、**核心诉求是元数据过滤**，RediSearch 直接支持 |
| 模型挂了怎么办 | 少重试（避免故障放大）→ 主备降级 → 熔断直接拒绝 → 兜底提示不白屏 |
| 重试越多越好吗 | ❌。重试次数越多降级越慢，外层重试要少，内层可稍多 |
| 熔断和降级区别 | 熔断是"**不再调用**"（保护自己），降级是"**换成备用方案**"（保住功能） |
| 流式为什么用 asyncEntry | `SphU.entry` 是线程本地的，流式回调可能在其他线程 |
| 降级为什么只能在首 token 前 | 流式输出已发出不可撤回，中途换模型会看到两段不同风格的文字 |

| fail-closed 是什么 | 默认拒绝 —— 判断不出权限就拒答，"答不出"比"答错"安全 |
| 为什么要三层隔离 | 因为索引过滤会**静默失效**，安全边界不能只依赖单层 |
| tenantId 从哪来 | **必须服务端从鉴权上下文推导**，绝不能信客户端传参 |

## 第 11 章 · 重点类精讲

> 本章收录单独问过的类的**逐类拆解**：字段 → 方法 → 执行流程 → 设计意图 → 面试关注点。
> 前面的章节按知识领域组织，本章按"类"组织，作为补充。

### 11.1 `DomainAwareRetriever` —— fail-closed 的实现者

**位置**：`llm/domain/DomainAwareRetriever.java`（`@Component`）

**一句话作用**：**按数据域授权检索**。它是"三层隔离"里第①②③层的执行者，也是全项目**安全语义最重**的一个类。

#### 依赖的三个东西

| 字段 | 类型 | 说明 |
|---|---|---|
| `publicStore` | `VectorStore` | 公共域向量库，`@Qualifier(VectorStoreConfiguration.BEAN_PUBLIC)` |
| `patientStore` | `VectorStore` | 患者域向量库，`@Qualifier(...BEAN_PATIENT)` |
| `properties` | `LlmProperties` | 取 `rag.topK` / `similarityThreshold` 与域名段名 |
| `filterWarningLogged` | `AtomicBoolean` | **索引过滤失效只警告一次**，避免每条请求刷屏日志 |

> ⚠️ 两个 `VectorStore` **必须用 `@Qualifier` 注进来** —— 它们都是同类型 Bean，不限定符会启动失败或注错。这也解释了为什么 `VectorStoreConfiguration` 里要用 `@Bean(name=...)` 显式命名。

#### 公开方法只有两个（重载）

```java
RetrievalResult retrieve(String question, Set<KnowledgeDomain> requested, String tenantId)
RetrievalResult retrieve(String question, Set<KnowledgeDomain> requested, String tenantId, String patientId)
boolean isAccessible(KnowledgeDomain domain, String tenantId)   // 诊断用
```

#### `retrieve()` 的七步流程

| # | 步骤 | 关键代码/行为 |
|---|---|---|
| 1 | **逐域裁决**（fail-closed） | `PATIENT && tenantId 为空` → 进 `denied` 集合并加 note，**不放行** |
| 2 | 都不可访问则短路 | `allowed.isEmpty()` → 直接返回空结果，**连向量库都不碰** |
| 3 | 逐域检索 | `fetch = max(topK, topK * 2)` —— **故意多取一倍** |
| 4 | 逐条 Java 复核 | `domain` 不符 → `violations++`（ERROR）；患者域 `tenantId` 不符 → `violations++`（ERROR）；`patientId` 不符 → `scopeMisses++`（WARN） |
| 5 | 合并后重排 | 按 `score` 降序 |
| 6 | **重新编号** | 丢弃原 index，按最终顺序重编 `[1]…[n]` |
| 7 | 截断到 `topK` | 只保留最相关的 `topK` 条 |

#### 四个容易被忽略但很关键的设计点

**① 为什么取 `topK * 2`？**
因为第 4 步的 Java 复核会**丢片段**。如果只取 `topK` 条，丢掉几条后就不够用了。**多取一倍是为了给安全的兜底层留余量** —— 这是个很典型的"纵深防御的成本意识"。

**② 为什么必须重新编号？**
因为检索是**按域分别做的**，公共域和患者域各自从 1 开始编号。合并后会出现两个 `[1]`，而 Prompt 里的引用编号必须是唯一的，否则模型引用和资料对不上、服务端的越界校验也失去意义。**重新编号保证 `[1]` 恒为最相关的那条。**

**③ 三类计数器为什么要分开？**

| 计数 | 级别 | 含义 | 处置 |
|---|---|---|---|
| `violations` | **ERROR** | 越域/跨租户片段被丢弃 | **安全问题**，必须立刻查 |
| `scopeMisses` | WARN | 非目标患者的片段被丢弃（但仍在授权机构内） | **精度问题**，说明索引过滤退化了 |

> 同一个"丢弃"动作，安全问题和精度问题的处置方式完全不同，所以**必须分开计数**。这也是前面 §5.5 讲的"可观测性"的落地 —— 日志级别本身就是一种分类。

**④ `search()` 的降级策略：不牺牲安全性**

```
带过滤表达式查询
   ↓ 抛异常（索引没建好 / TAG 值没转义）
退化为「无过滤查询」+ 只警告一次
   ↓ 仍失败
返回空结果继续（不抛给上层导致 500）
```
**降级的代价是"精度下降"（多捞了别的租户的片段再丢掉），但安全性由第 4 步的 Java 复核兜住。** 这就是为什么安全边界要分层：**上层可以降级，下层必须恒定。**

#### `escapeTagValue()` —— 全项目最值得记的一个方法

```java
static String escapeTagValue(String value) {
    // ASCII 非 [A-Za-z0-9_] 的字符 → 前面加 '\'
    // c > 127（中文等非 ASCII）→ 原样保留
}
```

规则很简单，但**少了它，患者域过滤会整条失效**（详见 §2.4）。两个细节：
- **为什么中文不转义**：实测 `@category:{\病历摘要}` 命中 0 条，而 `{病历摘要}` 命中 2 条 —— 转义后反而查不到
- **为什么是 `c > 127` 判断**：用字符码判断比用正则更直白，也避免正则元字符的二义性

#### 面试可能追问

- **"你怎么保证不会跨域读到数据？"** → 三层：未授权域不调用 VectorStore（最可靠）→ 索引过滤 → Java 复核。**并主动说出第②层会静默失效，所以才有第③层。**
- **"为什么多取一倍？"** → 给 Java 复核丢弃留余量。
- **"越域片段被丢弃了怎么办？"** → 记 ERROR 并计数，正常应为 0，一旦非 0 立即排查索引配置。

### 11.2 `IntentClassifier` —— 意图识别器

**位置**：`llm/route/IntentClassifier.java`（`@Component`）

**一句话作用**：**用加权关键字而不是模型**判断问题属于哪类临床意图，为后续的模型路由和数据域判定提供依据。

#### 为什么不调模型做分类？

类注释里写得很清楚，四个理由（这段值得背）：

1. **零延迟**：每次问答前多一次 LLM 调用，直接拖慢首字延迟
2. **零成本**：每次问答都多花一次 token 钱
3. **结果稳定**：模型分类**不可复现** —— 同一句话今天分到"用药咨询"、明天分到"通用问答"，路由行为就乱了
4. **可解释、可回归**：医疗场景里"**为什么这个问题走了便宜模型**"必须能解释、能写进验收用例

> **通用原则**：**能用规则判断的事就别用模型**。判断标准是"这件事是否需要理解语义"。意图分类只需要命中关键词，不需要理解 —— 那就用规则。

#### 关键字权重表（6 个意图）

| 意图 | 权重 | 为什么给这个权重 |
|---|---|---|
| `PATIENT_RECORD_QUERY` 患者病历 | **3.0** | **最高**。因为它决定**数据域是否放开**（`requiresPatientDomain=true`），宁可多判一次也不能越权 |
| `EMERGENCY_TRIAGE` 急诊分诊 | 2.0 | 危重场景，判错代价高 |
| `COMPLEX_REASONING` 复杂推理 | 1.5 | 决定是否走昂贵的推理模型 |
| `DRUG_QUERY` 用药咨询 | 1.2 | 常规领域意图 |
| `GUIDELINE_QUERY` 指南规范 | 1.2 | 常规领域意图 |
| `CHITCHAT` 闲聊 | 1.0 | 最低，最容易被误命中 |

> **权重的本质是"这个词有多专有"**：`"病历"`、`"既往史"` 几乎只出现在查病历的场景；而 `"你好"`、`"谢谢"` 可能出现在任何句子里，所以权重低。
> **再加上一条业务原则**：**越影响安全边界的意图，权重给得越高。**

#### `classify()` 的五阶段

```
① 加权打分        遍历 KEYWORDS，lower.contains(词) 就累加权重，并记录命中了哪些词
② 长度加成        长度 ≥ max(20, reasoningLengthThreshold=80) → COMPLEX_REASONING +1.0
③ 取最高分        严格大于（>）比较，所以同分时"先遍历到的"胜出
④ 追问继承        没命中任何关键字 && looksLikeFollowUp(q) && 有历史 → 继承上一轮意图
⑤ 兜底            → GENERAL_QA（"无关键字命中，按通用问答处理"）
```

**置信度算法**：`min(1.0, bestScore / 4.0)` —— 得分 4.0 即为满置信度。

**`looksLikeFollowUp()` 的判定**：
- 长度为 0 → false
- **长度 ≤ 15 → true**（短句大概率是追问）
- 否则遍历 `ANAPHORA` 指代词表（那 / 这个 / 它 / 还有 / 继续 / 详细说 / 展开 / 刚才 …），包含任一即 true

> `ANAPHORA` 的设计思路：**指代词是"上下文依赖"的语言信号**。"那这个患者呢"本身不包含任何医学关键词，但它显然依赖上文。

#### ⚠️ 两个已知小问题（读代码时发现的，值得记住）

**问题一：阶段⑤有条件死分支。**
```java
// 阶段④：looksLikeFollowUp(q) 对非空且长度 ≤ 15 的输入一定返回 true
if (previous != null && looksLikeFollowUp(q)) { return ...; }

// 阶段⑤：能走到这里说明 q 长度必然 > 15，所以 <= 12 永远不成立
if (previous != null && q.length() <= 12) { return CHITCHAT; }   // ← 死分支
```
**结论**：极短输入被判为 CHITCHAT 的那条路径**实际不可达**，短句会先被阶段④继承上一轮意图。想启用这条兜底，得把判断挪到阶段④之前。

**问题二：类注释与实现不符。**
- 注释写：`// 3. 选最高分。同分时按枚举声明顺序（= 业务优先级）决胜`
- 实际是：遍历的是 `scores`（`LinkedHashMap`），它的顺序来自 `KEYWORDS` 的**插入顺序**，而 `KEYWORDS` 的插入顺序是 `PATIENT_RECORD_QUERY → EMERGENCY_TRIAGE → COMPLEX_REASONING → DRUG_QUERY → GUIDELINE_QUERY → CHITCHAT`，**与枚举声明顺序不同**。
- 好消息是：这个插入顺序**恰好是按权重降序**（3.0 → 2.0 → 1.5 → 1.2 → 1.2 → 1.0），所以**实际行为是合理的**，只是注释说错了依据。
- **面试价值**：如果被问"你怎么保证同分时的行为可预测"，正确回答是"按 `KEYWORDS` 的插入顺序决胜，它按权重降序排列" —— 答"按枚举顺序"会被细心的面试官抓住。

#### 面试可能追问

- **"为什么不用模型做意图分类？"** → 上面四条理由，重点讲**不可复现**和**可解释性**。
- **"意图分错了会有什么后果？"** → 两个方向：分错成"患者病历"会触发数据域判定（可能拒答，但不会越权）；分错成"通用问答"会漏掉患者域检索（答不准）。**前者安全、后者可用 —— 所以权重宁可往安全那侧偏。**
- **"怎么验证分类器是准的？"** → 写用例集断言"这句话必须分到 XX 意图"，因为它是**纯函数、可回归**的（这正是用规则的好处）。

### 11.3 其余核心类速查

| 类 | 一句话作用 | 关键点 |
|---|---|---|
| `ModelRegistry` | 模型注册表，`@PostConstruct` 构建 | 缺 Key 的模型**跳过并告警**，不让应用启动失败 |
| `CapabilityRoutingStrategy` | 按意图能力选模型 | 是 `@Component`；**不要用 `@ConditionalOnMissingBean`**（M7 对嵌套 import 识别有问题） |

| `SimpleSlidingWindowGuard` | 自研滑动窗口实现 | 无 Sentinel 时兜底；`CANCEL` 信号只释放探测位不记失败 |
| `ChatFacade` | 模型调用门面 | 串起 **重试 → 主备降级 → 熔断**；`Flux.defer` 让许可申请发生在订阅时 |
| `ClinicalAssistantService` | 业务编排入口 | `prepare()` / `buildAnswer()` **同步与流式共用** —— 安全边界不能写两遍 |
| `RedisConversationStore` | 多轮会话存储 | `history-turns`(喂多少) 与 `max-stored-messages`(存多少) 是两个概念 |
| `PromptTemplateService` | 提示词模板 | 骨架分段复用：角色 / 行为约束 / 资料 / 数据域说明 / 免责声明 |

| `KnowledgeDomain` 枚举 | 数据域定义 | `PUBLIC` / `PATIENT`，各自带索引名与 key 前缀 |

【RAG 两阶段】
  索引期：文档 → 切分 → 向量化 → 入库(+元数据)
  查询期：问题 → 意图 → 权限 → 向量化 → 检索 → 拼Prompt → 模型 → 结构化

【三层隔离】物理隔离(独立索引/前缀) → 索引过滤(domain/tenant/patient) → Java复核
【fail-closed】判不出权限就拒答；未授权时"不检索、不调模型"

【降级链】少重试 → 切主备 → 熔断拒绝 → 兜底提示
【熔断三态】CLOSED 放行 / OPEN 拒绝(省时省钱) / HALF_OPEN 探测
【流式三坑】payload 必须 JSON / 熔断用 asyncEntry / 降级仅在首 token 前

【最狠的三个坑】
  1. TAG 值不转义 → 带连字符 ID 静默命中 0 条
  2. 框架默认重试 10 次 → 外层降级永远轮不到
  3. SSE 裸发文本 → 行首空格被吃、换行被拆
