完整生命周期

从 HTTP 进门，到变成一句能引用的回答。
8 个文件夹、10 个类、14 步调用。

01 全景

整条链路只有四段

① 接入
Controller 把 JSON 变成对象，然后交出去
② 准备
prepare 里做完全部判断，安全边界都在这
③ 调用
ChatFacade 选模型、熔断、重试、降级
④ 收尾
buildAnswer 把自由文本变成结构化对象
三条分支会在 ③ 之前提前返回：澄清、未授权、查无患者资料。
02 准备

prepare 里的七个判断

  • 载入会话 —— 拿到历史、租户、授权
  • 判意图 —— 这一问是常识，还是问具体病人
  • 要不要先澄清 —— 太短的问题先追问
  • 数据域授权 —— 没有 tenantId 直接拒答
  • 患者收敛 → 检索 → 拼 Prompt
所有安全判断都在调模型之前完成。模型是整条链路里最贵、最不可控的一环。
03 检索

三道闸门，一道比一道紧

① 物理隔离
没授权的域，对应的向量库根本不调用
② 索引过滤
查询里带 domain 与 tenantId 条件
③ Java 复核
返回后再逐条核对租户，不对就丢弃
坑：HOSP-A 里的连字符会被 RediSearch 当分隔符，过滤整条失效，必须先转义成 HOSP\-A。
04 调用

模型调用被包了四层

  • call() —— 在候选链上换模型，负责降级
  • invokeWithRetry() —— 同一个模型重试，只对 429 / 5xx / 超时
  • guard.execute() —— 熔断的进入、上报、退出
  • invokeOnce() —— 真正发 HTTP，一行容错都没有
每层只负责一件事，所以出问题能精确定位：是重试策略、熔断误开，还是模型真挂了。
05 收尾

拿到文本之后还有四件事

  • 剥掉 [META] 行 —— 那是给程序看的
  • 校验引用编号 —— 引用了不存在的 [5] 就是幻觉
  • 补齐免责声明 —— 不依赖模型是否照做
  • 写回会话 —— 下一轮追问才有上下文
同步和流式共用同一个 buildAnswer，所以两条路径的输出契约永远一致。
06 记住这三句

这个系统的设计原则

Controller 只做转换。
Service 只定顺序。
能在外围判断的，不交给模型。
