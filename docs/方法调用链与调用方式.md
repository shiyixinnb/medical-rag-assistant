```
   │     └─ ChatFacade.stream(chatRequestOf(p))                        [L164]
   │        ├─ decide(request)                                         [L119]

   │           └─ Flux.defer(() -> { ... })                            [L141]
   │              ├─ ModelCallGuard.guardStream(id, Supplier)          [L147]
   │              ├─ buildStream(model, request)                       [L188]
   │              │  └─ ChatClient...stream().content()                [L196]
   │              ├─ .map(ChatStreamEvent::delta)                      [L157]
   │              ├─ .concatWith(Flux.defer(...))                      [L159]
   │              │  └─ ChatStreamEvent.finished(meta)                 [L167]
   │              └─ .onErrorResume(...)                               [L171]
   │                 ├─ 已输出过 → Flux.error（不换模型）               [L176]
   │                 └─ 未输出过 → streamChain(idx+1)（换下一个）       [L182]
   ├─ Service 侧：.handle(...) → MetaStreamFilter.accept(delta)        [L165]
   ├─ Service 侧：.concatWith(...) → filter.flush()                    [L180]
   │              → buildAnswer(...) → AssistantStreamEvent.done(...)  [L192]
   ├─ emitter.send(SseEmitter.event().name(...).data(...))             [L116]
   └─ emitter.onCompletion/onTimeout/onError → subscription.dispose()   [L141-147]
```

**两条路径的汇合点**：`prepare()`（前）和 `buildAnswer()`（后）。中间那段完全不一样。

## 2. 六种调用方式

### ① 直接同步调用（最常见）

```java
RagAnswer answer = assistantService.ask(request);           // Controller
Prepared p = prepare(request, start);                       // Service 内部
session = conversationStore.loadOrCreate(sessionId, tenantId, allow);
```

依赖通过**构造器注入**拿到（`ClinicalAssistantService` 的 7 个依赖全在构造器里），调用时就是普通方法调用。

**判断依据**：需要返回值才能往下走 → 同步直接调。

### ② Builder 构造参数对象

```java
SearchRequest.builder()
    .query(question)
    .topK(fetch)
    .similarityThreshold(threshold)
    .filterExpression(buildFilter(domain, tenantId, patientId))
    .build();
```

用在**参数多、大部分可选**的场景。项目里三处典型：`SearchRequest`、`ChatRequest`、`RagAnswer`。

`RagAnswer` 有 18 个字段，如果不用 Builder，调用方要写 18 个参数的构造调用——没人记得住顺序。

### ③ 静态工厂（给对象起个名字）

```java
AssistantStreamEvent.meta(payload)      // 而不是 new AssistantStreamEvent("meta", payload)
AssistantStreamEvent.delta(text)
ChatTurn.user(question, intentLabel)
ModelAttempt.success(id, attempt, cost)
RetrievalResult.empty(note)
```

好处是**调用处能自解释**：看到 `ModelAttempt.blocked(id)` 就知道这是"被熔断拦下"而不是"调用失败"。

### ④ 响应式链式调用（流式专用）

```java
chatFacade.stream(chatRequestOf(p))
    .handle((ev, sink) -> { ... })          // 逐事件过滤
    .concatWith(Flux.defer(() -> { ... }))  // 结束后追加 done
    .onErrorResume(ex -> { ... });          // 出错兜底
```

三个必须知道的点：

- **惰性**：拼装 `Flux` 不会执行任何东西，**订阅时才跑**（`controller` 里的 `.subscribe(...)`）。
- `Flux.defer(...)`：把"申请熔断许可 + 构造上游请求"推迟到订阅时，否则第一个模型会被无意义地预热。
- `concatWith`：前面流结束后再接一段，`done` 事件就是这么发出去的。

### ⑤ 回调 / 模板方法（把代码块当参数）

```java
guard.execute(modelId, () -> invokeOnce(model, request));
guard.guardStream(modelId, () -> buildStream(model, request));
```

`ModelCallGuard` 的签名是 `<T> T execute(String resource, Supplier<T> action)`。

这是**装饰器语义**：真正的调用被包在参数里，熔断的"进入/成功/失败/退出"逻辑在外面统一处理。好处是业务代码完全不感知熔断的存在——`invokeOnce` 里没有一行熔断代码。

### ⑥ 递归下降（在候选链上换模型）

```java
private Flux<ChatStreamEvent> streamChain(..., int idx, ...) {
    if (idx >= chain.size()) return Flux.error(...);
    ModelDefinition model = chain.get(idx);
    return Flux.defer(() -> { ... return streamChain(..., idx + 1, ...); });
}
```

流式不能用 `for` 循环换模型（异步回调里没法 `continue`），所以改成"失败就递归调下一个 index"。这和同步版的 `for (idx...)` 是**同一件事的两种写法**。

### ⑦ 模板渲染

```java
promptService.render("rag_context", Map.of("context", block, "scope", scope));
```

读 `resources/prompts/*.st`，替换占位符，带缓存（`clearCache()` 可手动失效）。

## 3. 方法清单（按层）

### 3.1 编排层：`ClinicalAssistantService`

| 签名 | 谁调它 | 作用 | 返回值给谁 |
|---|---|---|---|
| `RagAnswer ask(AskRequest)` | Controller | 同步主流程 | 直接序列化成 HTTP 响应 |
| `Flux<AssistantStreamEvent> askStream(AskRequest)` | Controller | 流式主流程 | Controller 订阅后转 SSE |
| `Prepared prepare(AskRequest, long)` | 上面两个 | 调模型前的全部判断 | 自己用 / 拒答时直接出答案 |
| `ChatRequest chatRequestOf(Prepared)` | `ask` / `askStream` | 组装模型调用入参 | `ChatFacade` |
| `RagAnswer buildAnswer(...)` | 两条路径结尾 | 解析、校验、落库、组装出参 | HTTP / SSE done |
| `RagAnswer modelDownAnswer(...)` | 两条路径的 catch | 模型全挂时的兜底回答 | 同上 |
| `Map<String,Object> metaPayload(Prepared)` | `askStream` | 调模型前就能给的元信息 | SSE `meta` 事件 |
| `boolean shouldClarify(...)` | `prepare` | 是否先追问 | 分支判断 |
| `RagAnswer finishRefusal(...)` | `prepare` | 统一构造拒答 + 写会话 | 直接返回 |
| `String intentHint(QuestionIntent, ...)` | `prepare` | 按意图给模型额外提示 | 拼进 systemPrompt |

### 3.2 检索层：`DomainAwareRetriever`

| 签名 | 作用 | 注意 |
|---|---|---|
| `RetrievalResult retrieve(q, domains, tenantId)` | 不带患者收敛的检索 | 委托给四参重载 |
| `RetrievalResult retrieve(q, domains, tenantId, patientId)` | 主检索入口 | 三层防御都在这 |

### 3.3 模型层：`ChatFacade`

| 签名 | 作用 |
|---|---|
| `ChatResult call(ChatRequest)` | 同步：路由 → 逐个候选 → 熔断 → 重试 |
| `Flux<ChatStreamEvent> stream(ChatRequest)` | 流式：同上，但用递归下降 |

| `String invokeOnce(model, request)` | 真正的一次 HTTP 调用，不含容错 |
| `Flux<String> buildStream(model, request)` | 真正的一次流式调用 |
| `boolean isRetryable(Throwable)` | 429/5xx/超时 → true；401/403/400 → false |
| `void sleepBackoff(int attempt)` | 指数退避 |

| 签名 | 作用 |
|---|---|
| `ConversationSession loadOrCreate(id, tenantId, allow)` | 读取或新建会话；Redis 挂了退化成新会话 |

## 4. 三条设计约束（为什么非得这么调）

### 4.1 `prepare` / `buildAnswer` 必须两路共用

如果流式路径自己写一遍授权判断，迟早出现"同步拒答了、流式没拒答"。这类 bug 在演示时不明显，上线就是数据泄漏。

### 4.2 熔断必须包在调用外面

```java
guard.execute(id, () -> invokeOnce(model, request));   // 对：调用被包住
```

而不是：

```java
if (guard.isOpen(id)) return null;
return invokeOnce(...);                                // 错：漏了成功/失败上报
```

`isOpen` 只查状态，`execute` 才负责"记录本次成功/失败并触发状态迁移"。只调 `isOpen` 永远不会熔断。

### 4.3 流式降级只能在首 token 之前

```java
AtomicBoolean emitted = new AtomicBoolean(false);
...
if (emitted.get()) return Flux.error(ex);   // 已经吐字了，只能失败
return streamChain(idx + 1);                // 一个字都没发，才能换模型
```

否则用户会看到两个模型的答案首尾拼在一起。

## 6. 自测

1. `askStream` 返回的是 `Flux`，为什么 Controller 不直接返回它而要用 `SseEmitter`？
2. `ChatFacade.call` 里为什么 `isOpen` 和 `execute` 都要用？
3. `streamChain` 为什么用递归而不是 `for` 循环？
4. `Flux.defer` 去掉会发生什么？
5. `prepare` 里为什么 `retrieve` 在 `buildSystemPrompt` 之前？

<details>
<summary>参考答案</summary>

1. 返回 `Flux` 会占住 Tomcat 线程直到流结束；`SseEmitter` 让请求线程立即释放，并且断开/超时能显式 `dispose` 上游订阅。
2. `isOpen` 是快速跳过（熔断时不重试），`execute` 负责上报成败并驱动状态机；只有 `isOpen` 永远不熔断。
3. 异步回调里不能 `continue`；递归调用下一个 index 是等价的写法。
4. 第一个模型会在拼装 Flux 时就被申请许可（甚至预热），即使后面根本用不到它。
5. Prompt 里要注入检索到的资料；没检索就没有上下文，也就无法判断该不该拒答。

</details>
